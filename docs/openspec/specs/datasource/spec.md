# Datasource

Data sources (books via Open Library, movies and TV via TMDb), the per-user default and API key (Settings > Sources), and provider search for the add sheet, item details, the draft entry and the server-resolved add. List search (title substring on a list) belongs to filters-and-sorting (`media`), not here.

State: implemented through Phase 3 (`settings-module`, `datasource` and the Phase 3 change `media-search`, all archived). Search and details are `GET /search/books|movies` and `GET /search/{books|movies}/details` in the datasource module (`SearchController`); the add is `POST /books` and `POST /movies` in `media`, which calls the published catalog API of this module. The add sheet, preview and TV refresh are in `frontend/src/features/media/`. Open Library and TMDb are the only sources; data sources live in the data-source machinery of Phase 2 (sections from "Data sources" down).

Contract: `api/openapi.yaml`. Schema: `V001`. Add-sheet visuals: `docs/design/design-system.md`, flows: `docs/design/INTERACTIONS.md`.

## Requirements

### Requirement: Book search
The system SHALL search books by keyword in the selected book source through the backend, returning at most 10 provider hits in the source's order, each with a canonical `sourceUrl` generated by the server, title, main author, year, rating, cover and, when the provider returns one, the first non-blank ISBN as the provider gives it (not validated), followed by exactly one draft entry. Audiobook results SHALL be excluded. The selected source is the `source` parameter, else the user's effective source; an unknown `source` is 400.

#### Scenario: Search books
- **WHEN** the user types "Emma" in the add sheet
- **THEN** up to 10 books are listed with cover, title, author, year and rating, then the draft entry `Add "Emma" as draft`

### Requirement: Movie and TV search
The system SHALL search movies and TV in the selected movie source (TMDb: movies and series mixed, person results dropped), returning at most 10 hits with type (`movie` or `tv`), canonical `sourceUrl`, title, original title, description, year, rating and poster, followed by exactly one draft entry. TMDb results SHALL be available only when the user has a usable TMDb key.

#### Scenario: Search movies
- **WHEN** the user has a TMDb key and types "Top Gear"
- **THEN** movies and series are listed with poster, title, year, rating and type, then the draft entry

### Requirement: Search input behaviour
The add sheet SHALL search only for queries of 3 to 200 trimmed characters, debounce typing by 0.5 s, let the newest query win, cancel superseded requests silently, refetch when the source changes, mark results already in the library (row highlighted with a tick and not selectable), and disable provider search while offline. Row taps SHALL be ignored for 300 ms after the list changed (the draft entry moves while results arrive). A provider entry SHALL be marked when an item of the library has an `externalLink` equal, as a string, to the entry's `sourceUrl`, or, for a book hit that has an `isbn`, an equal normalized ISBN; the draft entry is not shown when the typed text equals a library title. The sheet SHALL offer no way to paste a raw link (the API accepts provider URLs, the UI deliberately does not). The sheet shows one status line under the field (offline, search unavailable, missing key, or "Searching in X"); the length hint shows only below 3 characters.

#### Scenario: Short query
- **WHEN** the query has fewer than 3 characters
- **THEN** no request is sent, a hint is shown and the local draft entry is offered

#### Scenario: Already in library
- **WHEN** a hit's `sourceUrl` equals the `externalLink` of a stored item
- **THEN** its row is highlighted with a tick and cannot be selected

#### Scenario: Offline
- **WHEN** the device is offline
- **THEN** provider search is disabled and only the draft entry is offered

### Requirement: Item details
The system SHALL provide details for a source URL (`GET /search/books/details?sourceUrl=`, `GET /search/movies/details?sourceUrl=`), used for the add-sheet preview and the TV refresh: for books author, description, cover, year, rating, ISBN and canonical link; for movies and TV type, original title, description, poster, year, rating, canonical link, and for TV series status (`ongoing` or `ended`) and number of seasons. The details SHALL be exactly the normalized record the server stores when an item is created from that URL; a draft link has no details (400 `validation` on `sourceUrl`). A provider item that does not exist is 404 `not_found` here (a create answers 422 `source_not_found`). TV status SHALL map `Ended` and `Canceled` to `ended`, other non-null values to `ongoing`, and null to unknown.

#### Scenario: Movie details
- **WHEN** details of a TMDb movie URL are requested
- **THEN** the description, poster, year, rating and original title are returned

#### Scenario: Draft link
- **WHEN** details are requested for a Google search link
- **THEN** the response is 400 `validation` on `sourceUrl`

#### Scenario: Preview equals stored
- **WHEN** details are fetched for a URL and the item is then created from it
- **THEN** the stored item has the values the details showed (same cache entry)

### Requirement: Preview
Every provider entry of the add sheet (not the draft entry) SHALL have an info control that opens a display-only preview sheet from the details of its `sourceUrl`, with an Add button pinned at the bottom that sends the same `{id, sourceUrl}` as tapping the row; the add sheet and the list beneath are inert while it is open. A failing preview SHALL show an inline error and never block adding. The info controls are disabled while an add is pending.

#### Scenario: Preview then add
- **WHEN** the user opens the preview of a hit and taps Add
- **THEN** the same `{id, sourceUrl}` is posted as for a row tap

### Requirement: Draft entry
Every search response SHALL end with one entry of kind `draft` carrying the typed text (trimmed) as title and, as `sourceUrl`, the Google web-search link of that text with the text fully percent-encoded as the `q` parameter (`https://www.google.com/search?q=<encoded>`); it is the last entry, below the provider hits, and the only one when the provider returns nothing. There SHALL be no separate "Can't find it?" block. When no server list is available (query under 3 characters, offline, provider error, unavailable source) the client SHALL build the same entry locally, so a draft is always one tap away. The server always returns the draft entry (it does not know the library); the client SHALL NOT show it at all when the typed text equals the title (movies: or original title) of an item already in the list (case-insensitive, trimmed, NFC), the rule the server enforces with 409. It is hidden, not shown disabled; provider entries already in the library stay visible but not selectable.

#### Scenario: Always last
- **WHEN** a search returns three hits
- **THEN** the list has four entries and the last one is the draft entry

#### Scenario: Nothing found
- **WHEN** the provider returns no hits
- **THEN** the response contains only the draft entry

#### Scenario: Offline draft
- **WHEN** the device is offline and the user types "Dune"
- **THEN** only the draft entry `Add "Dune" as draft` is available, built on the device, and adding it sends a plain create that fails while offline (online-first: nothing is queued, the outbox arrives in Phase 5)

#### Scenario: Draft already in the library
- **WHEN** "Dune" is in the library and the user types "dune "
- **THEN** no draft entry is shown; the provider results, if any, are listed, and a result that is already in the library is highlighted and cannot be selected

#### Scenario: Only the library title
- **WHEN** nothing but the draft entry would be listed and it is hidden because the title is in the library
- **THEN** the sheet shows the plain line "Already in your library" and no row

#### Scenario: Book hit with an ISBN
- **WHEN** a hit carries `isbn` `9780441172719` and a library book has the same normalized ISBN under another work id
- **THEN** the hit is highlighted as in library and cannot be selected

### Requirement: Server-resolved add
Adding an entry SHALL send only `{id, sourceUrl}` to the media API (the client UUID and the entry's canonical `sourceUrl`; the same call for provider entries and the draft entry; a pasted real provider page URL is accepted the same way). The server SHALL recognize the source and the provider id from the URL, SHALL NOT request that URL, SHALL fetch the item from the provider on its own configured base URL (Open Library, or TMDb with the user's key and locale), normalize it and store title, author, year, rating, description, cover or poster, ISBN, original title, seasons, TV status and the canonical `externalLink`; the client SHALL NOT submit any of them. The new item is `planned` and not favorite. The create SHALL NOT call the provider when the id is already live (200) or the provider item is already in the library (409 `duplicate`). A URL no source recognizes SHALL be 400 `validation` on `sourceUrl`. A failed resolve SHALL create nothing and be safe to retry with the same id. There SHALL be no automatic draft fallback; a draft remains an explicit user choice.

#### Scenario: Add a book
- **WHEN** the user taps a book entry
- **THEN** the client posts `{id, sourceUrl}`, the server fills the item from Open Library, and the sheet closes when the response arrives

#### Scenario: Paste a link
- **WHEN** a create carries `https://www.themoviedb.org/tv/1396-breaking-bad/season/1?language=ru-RU` on `/movies`
- **THEN** the server canonicalizes it to `https://www.themoviedb.org/tv/1396`, resolves the series and stores it with that link

#### Scenario: Unsupported URL
- **WHEN** the URL is an Open Library page on `/movies`, an unknown host or a non-http(s) scheme
- **THEN** the response is 400 `validation` on `sourceUrl`, nothing is fetched and nothing is created

#### Scenario: Already in library
- **WHEN** the URL names a provider item already held by a live item, in any spelling
- **THEN** the response is 409 `duplicate` with `existingId` and no provider request was made

#### Scenario: Retry with the same id
- **WHEN** the first attempt timed out on the client but was stored by the server and the client retries with the same id
- **THEN** the response is 200 with the stored item and no provider request is made

#### Scenario: TMDb unreachable
- **WHEN** the provider times out while resolving a TV URL
- **THEN** the response is 504 `provider_timeout`, no item exists, the add sheet stays open with the row enabled and a message inside the sheet offers Retry with the same id

#### Scenario: No TMDb key
- **WHEN** a movie URL is posted and the user has no saved TMDb key
- **THEN** the response is 409 `source_key_missing` with `source` `tmdb` and the sheet links to Settings

#### Scenario: Item gone at the provider
- **WHEN** the provider has no such item
- **THEN** the response is 422 `source_not_found`, nothing is created and the entry is removed from the results

### Requirement: Resolve does not hold the user write lock
The create SHALL NOT hold the per-user write lock or a database transaction while waiting for the provider; it SHALL re-check the id and the duplicates under the lock just before inserting.

#### Scenario: Slow provider
- **WHEN** a resolve is waiting on the provider
- **THEN** other writes of the same user complete normally

#### Scenario: Two devices add the same item
- **WHEN** two creates for the same provider item with different ids run concurrently
- **THEN** exactly one is created (201) and the other gets 409 `duplicate` with the first id

### Requirement: Add sheet source selector
The add sheet SHALL show a source selector only when the type's list has more than one available source; otherwise it only names the source in use. It SHALL preselect the effective source, and a choice made in the sheet SHALL NOT change the default (that is done in Settings). A source that is unavailable (it needs a key and none is saved) SHALL be explained in the sheet by name with a link to Settings, and the draft entry SHALL remain available.

#### Scenario: One available source
- **WHEN** a book list has only Open Library
- **THEN** no selector is shown and the sheet says "Searching in Open Library"

#### Scenario: Two available sources
- **WHEN** a type has two available sources
- **THEN** a selector is shown, the effective source is preselected, and choosing another sends its id as `source` without changing the default

#### Scenario: No TMDb key
- **WHEN** the user has no TMDb key and opens the movies add sheet
- **THEN** the sheet explains that TMDb needs a key, links to Settings, and the draft entry is still offered

### Requirement: Search error presentation
The client SHALL show failures of the add sheet and of the More menu inside the sheet (an alert area above the list or action), not as a floating toast: a failed search (per-kind wording naming the source, the local draft entry stays) and a failed add with Retry; a `Retry-After` replaces Retry by an inline countdown ("Try again in N s") until it is over, and the entry waits; key problems SHALL name the source from `Problem.source` and link to Settings (the link closes the sheet first); cancelled requests are silent. The problem mapping itself is "Search errors" below.

#### Scenario: Open Library down
- **WHEN** Open Library returns 500 during a search
- **THEN** the response is 502 `provider_error` with `source` `open_library` and the client shows the failure message inside the sheet with the draft entry still available

#### Scenario: Key missing names the source
- **WHEN** a movie search runs without a saved TMDb key
- **THEN** the response is 409 `source_key_missing` with `source` `tmdb`, and the sheet says that TMDb needs a key

#### Scenario: Rate limited with Retry-After
- **WHEN** an add answers 429 `rate_limited` with `Retry-After: 12`
- **THEN** the sheet shows "Try again in 12 s" counting down, then offers Retry with the same id

### Requirement: Search errors
Provider failures SHALL map to problems without provider bodies, URLs, queries or keys: connect or read timeout to 504 `provider_timeout`; 5xx, other 4xx, malformed or empty body to 502 `provider_error`, and any other client failure (without URI or message, no `source`) likewise; provider 429 to 503 `provider_rate_limited` with `Retry-After`; per-user limit to 429 `rate_limited` with `Retry-After`; a full outbound capacity to 503 `provider_error`; a source that needs a key used without one to 409 `source_key_missing`; the provider refusing the saved key (401) to 409 `source_key_invalid`; details not found to 404 `not_found`; a provider item that cannot be resolved on create because the provider has no such item to 422 `source_not_found`; a `sourceUrl` no source recognizes to 400 `validation` on `sourceUrl`; invalid query, unknown `source` or over-long URL to 400. The codes SHALL NOT name a data source; a problem about one source SHALL name it in the `source` member (`source_key_*`, `source_not_found`, `provider_error`, `provider_rate_limited`, `provider_timeout`; not `rate_limited`, not the full-capacity `provider_error`). The same codes apply to search, details, a create and saving a key (`PUT /data-sources/.../key`: 422 `source_key_rejected`, 504, 502, 503, 429, 400); the client presentation is "Search error presentation".

#### Scenario: TMDb down on key save
- **WHEN** the user saves a TMDb key and the key check times out
- **THEN** the response is 504 `provider_timeout` with `source` `tmdb` and nothing is stored

#### Scenario: Key missing names the source
- **WHEN** a movie reference is resolved for a user without a saved TMDb key
- **THEN** the catalog fails with `SourceKeyMissing` for `tmdb`, which the advice maps to 409 `source_key_missing` with `source` `tmdb`

### Requirement: Proxy hardening
The backend SHALL call only the configured provider base URLs; it SHALL treat a client `sourceUrl` as data to parse (strictly: http or https, exact allowed host, no userinfo, default port only, no trailing dot, raw path matched against a fixed pattern, at most 4096 characters) and never as a target; validate provider ids (Open Library `OL<digits>W`, TMDb digits without leading zero, type `movie` or `tv`) and queries before any outbound call; use connect 3 s and read 8 s timeouts without retries, cap responses at 2 MB, not follow redirects, rate-limit per user (search 30/min with a burst of 10 per 10 s, details 60/min with a burst of 20, key save 5/min with a burst of 5) with at most 8 concurrent outbound calls (a call over the limit is rejected at once with 503 `provider_error`), identify itself to Open Library with a User-Agent containing a contact, and never log keys, outbound URLs, `sourceUrl`s or query text above DEBUG. URL recognition SHALL run before any rate-limit token is spent. Normalized public results MAY be cached in memory for 10 minutes; the cache SHALL NOT hold keys. Clients SHALL render a link only when it is an https URL.

#### Scenario: SSRF
- **WHEN** a `sourceUrl` is `http://169.254.169.254/works/OL1W`, `https://openlibrary.org@evil.com/works/OL1W` or `https://openlibrary.org.evil.com/works/OL1W`
- **THEN** the recognizer yields no reference (400 `validation` on `sourceUrl`) and no outbound request is made

#### Scenario: Rate limit
- **WHEN** a user saves a key 6 times within a minute
- **THEN** the 6th returns 429 `rate_limited` with `Retry-After` (the search and details buckets use the same limiter; a create that resolves spends a details token)

### Requirement: TV refresh
The movies list SHALL offer an explicit "Refresh series status" action in its More menu (a sheet; Books has no More button) that fetches details (`GET /search/movies/details` by the stored `externalLink`) sequentially for TV items whose `source` is not `draft` and updates an item only when status or season count differs and the new status is non-null, through the normal media write (`PATCH /movies/{id}`). An item the provider no longer has (404 `not_found`, 422 `source_not_found`) or whose link is invalid (400 on `sourceUrl`) SHALL be skipped. It SHALL stop with a message inside the sheet on a `source_key_*` error (with an Open Settings action that closes the sheet first) or any other failure, in wording that fits a refresh (never "nothing was added"); series already written stay written. On a rate limit (429 `rate_limited` or 503 `provider_rate_limited`) it SHALL wait `Retry-After` seconds (5 s without the header) and retry the same series once, a second rate limit for that series stops the run. Closing the sheet stops the run; the result line reads "Series checked: N. Updated: M.".

#### Scenario: Status changed
- **WHEN** a series was `ongoing` and TMDb now reports `ended`
- **THEN** the item is updated through the normal media write

#### Scenario: Key invalid
- **WHEN** the refresh gets 409 `source_key_invalid`
- **THEN** it stops with a message naming the source and an Open Settings action inside the sheet

#### Scenario: Rate limited once
- **WHEN** a series answers 429 with `Retry-After: 2`
- **THEN** the run waits 2 s and retries that series once

### Requirement: Per-user isolation
Key reads, writes and rate limits SHALL be scoped to the signed-in user; one user SHALL NOT use or observe another's key. An isolation test SHALL cover this.

#### Scenario: Other user
- **WHEN** user B searches TMDb without a key while user A has one
- **THEN** user B gets 409 `source_key_missing` with `source` `tmdb`

### Requirement: Data sources
The system SHALL offer data sources per type, each type with its own ordered list and its own configured default (`rwx.datasource.books.default` / `.movies.default`; the first listed source when unset). Today books have Open Library and movies and TV have TMDb. A source SHALL have an id, a label, whether it needs an API key, a per-user availability, a way to recognize its own page URLs, a way to search and to resolve an item and, when it needs a key, a way to validate one; adding a source SHALL NOT change the API shape. `GET /data-sources` SHALL return both lists with, per source, whether it is the user's default (`isDefault`), whether a search without `source` uses it (`isEffective`), whether it is available and whether a key is saved (`tokenSaved`). A source that is unavailable (it needs a key and none is saved) is reported as such by `GET /data-sources`; the add sheet explains it (see "Add sheet source selector").

#### Scenario: Lists per type
- **WHEN** an authenticated user calls `GET /data-sources`
- **THEN** `books` lists Open Library (available, no key needed) and `movies` lists TMDb (needs a key, unavailable until one is saved), each with `isDefault`, `isEffective`, `available` and `tokenSaved`

### Requirement: Published catalog API
The `datasource` module SHALL publish a catalog API that identifies a source URL (pure, no I/O) into a provider reference (source, provider id, movie or tv type, canonical URL), resolves a reference for a user into a normalized item or fails with a typed catalog error; `datasource` SHALL NOT depend on `media`, and the consumers (the details endpoints and the create in `media`) SHALL use the same recognition, resolution and short-lived cache. The source SPI SHALL be internal to `datasource`. Provider values SHALL be normalized at ingest: bounded text lengths, ratings clamped, years in range, ISBN taken as the provider gives it (first non-blank, trimmed, not validated), covers and page links built by the server and never copied from the provider or the client; a missing title is the only provider-data error (502).

#### Scenario: Link canonical
- **WHEN** a canonical URL built by a source is re-submitted to the recognizer
- **THEN** it yields the same reference and the same canonical URL

### Requirement: User data sources
A user SHALL be able to make a source the default of a resource type (books and movies each have their own default) and to save an API key for a source that needs one. The state SHALL be stored per user, resource type and source: every user SHALL have exactly one default row per resource type, inserted when the user is created (the configured default of the type, no key); another row exists only for a saved key, and a row holding neither SHALL NOT exist. If the stored default's source is no longer registered, the configured default applies. A user SHALL have at most one default per resource type. Setting a default SHALL be idempotent and allowed for any registered source of the type, available or not. A key operation on a source that needs no key, or any operation on a pair of resource type and source that is not registered, SHALL be 404 `not_found`. Every read and write SHALL be scoped to the signed-in user.

#### Scenario: New user
- **WHEN** a user signs in for the first time and lists the data sources
- **THEN** the configured default of each type is the default (and the effective source when available), no key is saved, and the user has exactly one stored default row per type, written at sign-up

#### Scenario: Choose a default
- **WHEN** the user makes the second movie source the default and then the first
- **THEN** exactly one movie source is the default at any time and the book default is unchanged

#### Scenario: Setting the same default twice
- **WHEN** the same source is made the default twice
- **THEN** both calls succeed and nothing changes the second time

#### Scenario: Not registered or no key
- **WHEN** the user sets a default for a source that is not a source of that resource type, or saves a key for Open Library
- **THEN** the response is 404 `not_found` and nothing is stored

#### Scenario: Another user
- **WHEN** user B lists, sets a default or deletes a key
- **THEN** user A's defaults and keys are neither visible nor changed

### Requirement: Effective source
The effective source (`isEffective` in `GET /data-sources`, and what a search without `source` uses) SHALL be the effective source of the type: the user's default when it is available, otherwise the first available source in list order, otherwise the default (its own key problem is then reported). The fallback SHALL NOT change the stored default: when the key of a default source is deleted the choice is kept, the source becomes unavailable and the effective source moves on, and saving a key again makes it effective again. Deleting the key of the default keeps its row without the key; deleting the key of a source that is not the default SHALL leave no row for it. Resolving a reference and URL recognition SHALL NOT depend on the default.

#### Scenario: Default without a key
- **WHEN** the user made a key-requiring source the default and deletes its key
- **THEN** the source stays the default but is unavailable, the effective source is the first available one, and `isEffective` moves to that one

#### Scenario: Key saved again
- **WHEN** the user saves the key again
- **THEN** the source is the default and effective again

#### Scenario: Only one source and no key
- **WHEN** the only source of a type needs a key and none is saved
- **THEN** it stays the default and effective, and a resolve answers `SourceKeyMissing` naming the source (409 `source_key_missing` at the HTTP surface)

#### Scenario: Pasted URL ignores the default
- **WHEN** a TMDb reference is resolved and the user's movie default is another source
- **THEN** the item is resolved at TMDb with the user's TMDb key

### Requirement: Per-user API key
A source that needs a key (TMDb: a v4 read access token, preferred and requested by the UI, or a v3 API key) SHALL use the key saved by the user. Saving SHALL first validate the key with the source: accepted means stored; rejected means 422 `source_key_rejected` naming the source and nothing stored (an older key stays); network failure or timeout means 502 or 504 and nothing stored; a key that breaks the source's format is 400. Saving again SHALL replace the stored key and SHALL NOT change the default. Deleting SHALL remove the key immediately and is idempotent. A later 401 from the provider SHALL report 409 `source_key_invalid` without deleting the key (no key status is kept or returned). The key is stored as is until the owner decides on encryption and SHALL never be returned (no response carries it or any part of it, such as the last characters), logged, or put in an error message; it is not synced, cached on the client or exported.

#### Scenario: Invalid key
- **WHEN** the provider answers 401 to the validation call
- **THEN** the response is 422 `source_key_rejected` with the source named and no key is stored

#### Scenario: Network error on save
- **WHEN** the validation call times out
- **THEN** the response is 504 and no key is stored

#### Scenario: Key expires later
- **WHEN** a search gets 401 from the provider
- **THEN** the response is 409 `source_key_invalid`, the key is kept

#### Scenario: Key never read back
- **WHEN** any endpoint is called after saving
- **THEN** no body contains the key

#### Scenario: Delete key
- **WHEN** the user deletes the TMDb key
- **THEN** TMDb is no longer available in the add sheet

### Requirement: Sources settings UI
Settings SHALL show a "Sources" section fed by `GET /data-sources`: per resource type its sources with a label and state (available, needs a key); every row has the same shape; a source that needs a key shows its state as a button that opens a dialog with a write-only field (masked placeholder when saved, no reveal control), Save or Replace, a red trash button beside the field when a key is saved (Remove), a hint and a link under the field explaining how to get the key, and an error message per problem code naming the source (a failure keeps the dialog open and the field focused and is shown right under the field in a reserved one-line slot (a longer message grows the dialog by the difference), so the dialog keeps its size; editing the key clears it; saving closes the dialog, removing the key keeps it open and offers Save); and, only for a type with two or more registered sources, a control to choose the default. The default control SHALL accept an unavailable source and then show a short hint on that row (add a key or switch the default) instead of naming another source; the selected radio alone marks the default (no "Default" label). A ready source (no key needed, or a key saved) shows "Available" in green. The three mutations SHALL replace the cached `GET /data-sources` result with the response, so every consumer sees a change at once. Caching the list on the device for offline use belongs to the Offline/PWA phase.

#### Scenario: Add key
- **WHEN** the user saves a valid key
- **THEN** the list shows `tokenSaved` true and TMDb is `available` in the movies list

#### Scenario: One source per type
- **WHEN** every type has a single registered source
- **THEN** no default control is shown

#### Scenario: Choose a default
- **WHEN** a type has two sources and the user selects the second as the default
- **THEN** it is `isDefault` and, while available, `isEffective`

## Decisions (formerly open)
- TMDb results are requested in the language of the user's device locale (`user_settings.locale`: en, ru or uk, never null); Open Library is language-independent.
- A URL no source recognizes is invalid input: 400 `validation` on `sourceUrl` (owner decision 2026-11-19); there is no `unsupported_source` code.
- The add sheet has no paste affordance; the API accepts pasted provider links.
