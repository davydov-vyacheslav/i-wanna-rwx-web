# Design: media-search (Phase 3)

Split out of the former combined `media-search` change on the Phase 2 re-plan (owner decision): everything about the product side of search and the add flow. The provider machinery (sources, SPI, keys, defaults, resolvers, rate limit, error mapping, packages) is in `docs/openspec/changes/archive/datasource/design.md` (Phase 2); section numbers below keep the numbers of the old combined design so that cross references stay readable (8, 12 create flow, 13). Prerequisites: `media-core` merged, `datasource` done.

## 8. Frontend design
- Add sheet = media-core shell (F10: entry list, draft entry, create by `sourceUrl`) + provider search. `GET /data-sources` is fetched online; if it fails the sheet shows the local draft entry only (Dexie caching of sources is deferred to `offline-sync`). Per type the sheet preselects the source marked `isEffective` (the server applies the default-or-first-available rule, the client does not repeat it); picking another source in the selector is a one-off choice for that sheet and never changes the default (that happens only in Settings > Sources). The source selector (segmented control or menu, with the "Searching in <label>" line) is rendered ONLY when the type's list has more than one available source; with one it is just the line. If no source is available (TMDb without a key): the sheet explains why (naming the source from the list) and links to Settings > Sources, and the draft entry remains.
- Search rules (search spec): min 3 characters, 0.5 s debounce, TanStack Query with `signal` for cancellation and the source id in the query key (switching source refetches), newest query wins, error toast 3 s (cancelled = silent), 3 characters minimum otherwise only the local draft entry. The result list is the server array as it is: provider entries, then the draft entry last, below them. The separate "Can't find it?" block is gone. If the server list is unavailable (under 3 characters, offline, error, unavailable source) the sheet builds the same draft entry locally with `draftLink(text)`, so a draft is always one tap away.
- In library: a provider entry whose `sourceUrl` equals an item's `externalLink` (string equality), or a book hit whose `isbn` equals an item's (`normalizeIsbn` on both), stays visible, highlighted with a tick and not selectable. The draft entry is NOT shown at all when `titleKey(text)` equals the title key of any library item's title (movies: or original title); there is no disabled draft row. If that leaves nothing to list the sheet shows the plain line "Already in your library". The server's 409 remains the backstop when the library is not loaded. The library list is the TanStack Query cache of media-core (design there, 11.5).
- Add from an entry (two taps): tapping a selectable entry sends `create({id, sourceUrl})`, nothing else; same call for a provider entry and for the draft entry. The row shows a pending state (spinner, disabled) until the server answers (typically 1-3 s for providers, instant for drafts, up to ~10 s); no optimistic card online. 201/200 closes the sheet and the card comes from the response. Failures keep the sheet open and the row enabled: 409 `duplicate` adopts `existingId` ("already in library", select it); 409 `source_key_missing`/`_invalid` -> message with a link to Settings > Sources; 422 `source_not_found` -> "no longer available", entry removed; 422 `unsupported_source` -> generic error toast (a stale client); 429/503 (honour `Retry-After`), 502, 504 -> toast with Retry. A retry reuses the same `id` (idempotent: if the first attempt succeeded server-side and only the response was lost, the retry returns 200); a new `id` only after success, or when an entry with another `sourceUrl` is tapped. The POST timeout is 15 s. There is no automatic draft fallback: the draft entry is always shown and chosen by the user.
- Preview (optional, not an extra step): an info affordance on a provider entry opens a sheet from `getBookDetails`/`getMovieDetails` called with the entry's `sourceUrl` (description, poster/cover, year, rating, TV status/seasons) with an Add button that posts the same `{id, sourceUrl}`. Display only; the add re-resolves on the server (usually from the 10-minute cache).
- Paste a link: the API accepts a real provider page URL on create and on the details endpoints (section 15.3). The UI deliberately offers no affordance to paste a raw link (owner decision, revision 3.1); the add sheet takes search text only.
- TV refresh: explicit action in the movies list menu; sequentially calls `getMovieDetails` with the stored `externalLink` of TV items whose `source` is not `draft`, writes only when `tvStatus` or `seasonCount` differ and the new status is non-null; stops with a toast on `source_key_*`, backs off on 429. Write path: `PATCH /movies/{id}` with `seasonCount`/`tvStatus`.
- Settings "Sources" (frontend F4, fills the `settings-screen` slot): one `useDataSources()` query on `GET /data-sources` shared with the add sheet; the three mutations (`setDefaultDataSource`, `saveDataSourceKey`, `deleteDataSourceKey`) replace the query data with the returned lists, so the add sheet reflects a change at once. Two groups (Books, Movies and TV), one row per source with its label and state (available / key saved / needs a key). A default choice control (radio among the sources of the group) is shown only for a group with two or more registered sources, so it is invisible while each type has one; it allows an unavailable source (the row then says which source is used instead until a key is saved). For a source with `requiresKey`: the write-only key field with a masked placeholder when saved (no reveal), Save / Delete, a "how to get a key" link (TMDb: v4 read access token), error text per `code` (`source_key_rejected` = wrong key, naming the source from `Problem.source`).
- Rendering links: only `https` URLs are links (`safeHttpsUrl`), `rel="noopener noreferrer"`, `target="_blank"`; a hit's `sourceUrl` is used only as the create input and the equality key, never navigated to unless it passes the check (the draft entry's link is not shown as a link in the sheet).
- CSP/Workbox: `img-src` allows `covers.openlibrary.org` and `image.tmdb.org`; covers cached by the service worker later (Phase 5, Offline/PWA).

## 12. Server-resolved add by source URL (create flow in `media`; the published catalog API is section 12 of `datasource/design.md`)

### Create flow in `media` (provider URL; the draft path is media-core B14)
`BookService.create(userId, id, sourceUrl)` and the movie twin are not transactional at the top level (open-in-view is off, so no DB connection is held while waiting on HTTP):
1. Read (no lock): row with this `id`: live -> 200 with the stored record, no URL inspection, no provider call; tombstone -> 410.
2. Recognize: the draft-qualified `MediaResolver` (`@Qualifier(MediaResolver.DRAFT)`) `identify(url)` first, then `resolve` (-> draft path, media-core; empty when the URL is not a draft link), else `catalog.identify(url)`; neither -> 422 `unsupported_source` (replaces media-core's temporary behaviour for every non-draft URL).
3. Read (no lock): live row with the same (`source`, `externalId`) (movies: also `type`) -> 409 `duplicate` with `existingId`, no provider call. This is why the identity comes from the URL: the check costs no provider round trip and catches pasted URLs in any form (slug, trailing path, query) as the same item.
4. `catalog.resolve(userId, ref)`. The key check happens inside, after steps 1-3, so a re-POST of an existing id works without a key. Any `CatalogException` propagates: nothing was written.
5. Build the content (`source`, `externalId`, `externalLink` from the ref, `planned`, not favorite), assert the stored-item invariants (violation -> `ProviderError`).
6. Short transaction: `UserWriteLock`, repeat steps 1 and 3 plus the ISBN duplicate rule, insert, 201. A lost race resolves to 200 (same id inserted meanwhile) or 409 (same item under another id), never a 500.
- Lock strategy and trade-off (unchanged from revision 2): the per-user lock is NOT held across the provider call. Holding it would block every write of that user (a favorite toggle, a delete) for the length of a slow provider call (bounded by the per-request timeouts) and pin a Hikari connection per slow call. Cost of resolving first: two concurrent creates of the same item both call the provider before one of them loses at step 6, so one provider call is wasted (the cache usually absorbs it); an ISBN duplicate is only found after the resolve. Rejected: lock across HTTP; a pending placeholder row (leaks into lists, pull and `change_seq`, needs a state machine); a per-(user, source, id) single-flight map (extra state, add if provider cost ever matters).
- Failure policy: a failed resolve creates nothing and consumes no `change_seq`; there is no draft fallback. Retrying with the same id is safe. Codes: section 6; `Retry-After` for `rate_limited` and `provider_rate_limited`.
- Idempotency: a re-POST of the same id returns 200 with the stored record and the body is ignored, also if the body now names another URL (existing rule).

### What the client can still write
Status and favorite (PATCH), tv `seasonCount`/`tvStatus` (PATCH: the TV refresh stays client-driven; it is the one place where client-submitted provider data remains), delete. Everything else is immutable for the client. Promoting a draft later is possible without reworking the contract: a new operation taking a provider `sourceUrl`, re-using the flow and the duplicate rule and filling the draft's fields in place (keeping id, status, favorite); it needs one exception to the immutability of `source`/`externalId`. Not in v1.

## 13. Offline-sync consequences (delta: `docs/openspec/changes/offline-sync/specs/offline-sync/spec.md`)
- The outbox carries `BookUpsertPayload`/`MovieUpsertPayload` (`id`, `sourceUrl`, status/favorite). The server recognizes and resolves the URL when the mutation arrives, so a queued add stays small and valid and the client stores no provider fields. A draft's `sourceUrl` is built on the device with `draftLink(text)`, so drafts work offline exactly as before.
- Search is disabled offline, so a queued provider URL exists only when an online add was interrupted; the optimistic row is built from the tapped entry (title, cover, `sourceUrl` as `externalLink`; display only) and replaced by the server record from the push result or pull.
- Push handler rule for `MediaMutations`: recognize first (`unsupported_source` -> `rejected`, permanent), identity pre-check, resolve outside the per-mutation transaction, then one short transaction (idempotency record, user lock, insert). A transient provider failure -> `deferred` (not recorded in `applied_mutations`, stays queued, followers of the same record deferred too); a permanent one -> `rejected` with `unsupported_source` / `source_not_found` / `source_key_missing` / `source_key_invalid`. At most 10 provider resolutions per push and the details rate limit apply; the rest are `deferred`. Drafts never call a provider and are not counted.
- An upsert for an existing record: the identity derived from the payload (`source`, `externalId`, and `type` for movies; for a draft the `externalId` is the normalized text) must equal the stored one (`immutable_field` otherwise) and only status/favorite are applied; duplicates, 410 and idempotency are as on REST.
