# Design: identity-github-oauth

Sources of truth: V001 (schema), `api/openapi.yaml` (contract), `docs/openspec/specs/identity/spec.md` (behaviour).

## 1. Data
No new migration: the Spring Session JDBC tables (`SPRING_SESSION`, `SPRING_SESSION_ATTRIBUTES`, DDL verbatim from spring-session-jdbc 4.1.1) are part of V001, which is edited in place until the first deploy; `spring.session.jdbc.initialize-schema=never`, and Hibernate does not map them so `validate` is unaffected. `users` has id, timestamps, `disabled_at`; login, name and avatar live in `credentials.data` (refreshed on every login); timezone/locale in `user_settings`, created with the user (default `UTC`). `credentials.external_id` for GitHub is the numeric GitHub id, never the login. No secrets table; the GitHub access token is not stored; the client secret comes from the environment.

## 2. Login flow
Built on Spring Security `oauth2Login` (spring-boot-starter-security-oauth2-client); no hand-written protocol code. Registration `github` comes from `spring.security.oauth2.client.registration.github.*` (client id/secret from `RWX_GITHUB_CLIENT_ID/SECRET`, scope `read:user`, redirect URI `{baseUrl}/api/v1/auth/github/callback`); GitHub's endpoints are Spring's built-in `github` provider and can be overridden with `spring.security.oauth2.client.provider.github.*` (the tests point them at a local stub).
1. `GET /oauth2/authorization/github` (Spring's default authorization path; not in the OpenAPI contract, the SPA just navigates to it). State lives in the session (Spring's session repository wrapped in the provider-agnostic `ShortLivedAuthorizationRequestRepository`, which gives a purely pre-auth session a 10-minute TTL). Redirect to GitHub. PKCE decision: no custom code. The client is confidential (secret + `state`), so PKCE is not required; Spring Security 7's default resolver nevertheless adds `code_challenge` (S256) and the verifier, and GitHub accepts it, so it stays on at zero cost (`GithubLoginTests` asserts it). To switch it off: `.authorizationEndpoint(ae -> ae.authorizationRequestResolver(r))` with a `DefaultOAuth2AuthorizationRequestResolver` whose `setAuthorizationRequestCustomizer(c -> c.attributes(a -> a.remove(PkceParameterNames.CODE_VERIFIER)).parameters(p -> { p.remove("code_challenge"); p.remove("code_challenge_method"); }))`. Earlier drafts had a custom resolver serving `/auth/github/start`; it is deleted.
2. `GET /auth/github/callback` is handled by `OAuth2LoginAuthenticationFilter` (redirect endpoint base URI set to the contract path, which is what is registered on the GitHub OAuth App): state check, code exchange, user-info call. The pending request is single use.
3. `GithubOAuth2UserService` wraps `DefaultOAuth2UserService`, maps id/login/name/avatar to the neutral `ExternalProfile(provider, externalId, login, name, avatarUrl)` and calls `AccountService.loginOrCreate` (known credential: refresh metadata and `last_used_at`; unknown: user + credential of type `provider` + `user_settings`, open sign-up; `disabled_at` set: `AccountDisabledException`, rethrown as an `OAuth2AuthenticationException` with that cause). Concurrent first logins of one identity are handled by `@Retryable` (Spring Framework 7, `@EnableResilientMethods`) on the `@Transactional` method: the loser's transaction rolls back on the unique violation and the retry finds the winner's credential. The returned principal is `UserPrincipal(userId)` (it implements `OAuth2User` with no attributes, so no GitHub data is kept in the session).
4. The session id is rotated by the filter's session strategy (fixation). `LoginSuccessHandler` restores the 30-day TTL and redirects to `/`. There is one generic failure for everything (user cancelled, disabled account, missing/forged/replayed state, provider error): 302 to `/login?error`, no reason, no 400, no session. The failure handler is a small lambda around `DefaultRedirectStrategy`, not `SimpleUrlAuthenticationFailureHandler`: that one saves the exception into an existing (pre-auth) session and the JDBC session store cannot serialize it. The handler never touches any session, so the old guard (drop only purely pre-auth sessions) is unnecessary and a forged callback cannot end a signed-in session (`forgedCallbackNeverEndsASignedInSession`); a pre-auth session expires after its 10 minutes. A disabled account fails inside `GithubOAuth2UserService`, so no session is created. Distinctions (`access_denied`, `disabled`, `provider_error`, `invalid_oauth_state`) were dropped on purpose; the server logs nothing for them.
5. The access token is never stored or logged: the `OAuth2AuthorizedClientRepository` is a discarding implementation, and the security context holds only the `OAuth2AuthenticationToken` with `UserPrincipal`.
`loginPage("/login")` is set deliberately: it stops Spring from serving its generated login page at `/login`, which is the SPA's route. There is no `AuthController`: the generated `AuthApi` has no implementer (the filters answer the callback and logout before the dispatcher). Logout is Spring Security's: `POST /api/v1/auth/logout`, invalidate session, delete the `SESSION` cookie, `HttpStatusReturningLogoutSuccessHandler(204)`; it stays idempotent (204 without a session) and the CSRF exemption applies only when no client session exists. `GithubOAuth2UserService` reads GitHub's attribute names (`id`, `login`, `name`, `avatar_url`), so it stays in the github package; the provider stored is the registration id. Known gap: Spring's token and user-info calls have no explicit connect/read timeouts.

## 3. Sessions and CSRF
Spring Session JDBC, cookie `SESSION` (HttpOnly, SameSite=Lax, Max-Age 30d, Secure follows the request scheme so it is set behind Traefik and off on localhost), 30-day rolling idle timeout. The cookie is configured by an explicit `CookieSerializer` bean (`SecurityFoundationTests` checks the flags); replacing it with Boot properties is parked in `docs/TODO.md`. CSRF: `CookieCsrfTokenRepository` (readable `XSRF-TOKEN` cookie), client echoes in `X-XSRF-TOKEN`; GET is exempt. Same-origin, no CORS. 401 and 403 are `application/problem+json`, built in one place: the security entry point and access-denied handler delegate to the `handlerExceptionResolver` bean, and `ProblemAdvice` (the single `@RestControllerAdvice`) maps `AuthenticationException` and `NotAuthenticatedException` to 401 `unauthorized`, `CsrfException` to 403 `csrf`, `AccessDeniedException` to 403 `forbidden`; details are static. `/oauth2/authorization/**`, `/auth/github/*` and actuator probes are public; everything else needs a session. Logout is idempotent.
In the Vite dev server the cookie works because `/api` is proxied; the GitHub callback URL points at :8080, so the OAuth round trip finishes on the backend origin; the SPA served by the jar on :8080 is the supported place to test login (note in README).

## 4. Published API and isolation
- `com.javanix.rwx.identity`: `record CurrentUser(UUID id, ZoneId timezone)`, `interface CurrentUserProvider { CurrentUser current(); }` throwing `NotAuthenticatedException` (401 problem). The implementation reads the principal from the security context and loads the timezone from `user_settings` (one PK lookup, so a timezone change applies immediately). Entities, repositories and security config are internal.
- `UserTimezoneChangedEvent(userId, old, new)` is published by identity when the stored zone actually changes (from `/me` or `/settings`, one service); no listeners yet.
- `/me` and `/settings` share `AccountService`, which also owns login-or-create, profile and account deletion (repositories plus `@Transactional`, no raw SQL); entity to DTO mapping is MapStruct (`IdentityMapper`). Validation: schema rejects an empty body and a locale outside `en|ru|uk` (400 `validation`); a zone outside `ZoneId.getAvailableZoneIds()` is 400 `invalid_timezone`. Nothing changes on a 400.
- `DELETE /me`: one transaction, sessions of the user removed through the session repository, `users` row deleted through the repository (cascade), 204. Push subscriptions are cleared on `pushNotificationsEnabled=false` by a minimal repository in identity until the push module owns the table. `GET /me/export`: `AccountExport` with live records only; for domain data not yet existing (books and so on) the sections are empty arrays now and modules contribute later through a published export contributor interface (identity defines it, media/reminders implement it). Never the TMDb key or session data.
- Isolation rules for every later module: `user_id uuid not null` first in keys, repositories expose only user-scoped finders, cross-user access is 404, architecture test per module.

## 5. Tests without a bypass
Test sources only: `TestUsers` helper creates user + credential + settings through the identity internals' test fixtures and returns a `MockMvc` request post-processor (or session cookie) that carries a real saved session; `TwoUsersFixture` (A and B) and `assertNotFoundFor(userB, requestOnAsResource)` build on it. Nothing in `src/main` knows about tests. GitHub is stubbed with WireMock (external HTTP is the only allowed stub). This kit is what `media-core` B8 and the other isolation suites use.

## 6. Frontend
- `useMe()` (TanStack Query, key `['me']`); 401 means signed out, shown as the login page. The API client attaches `X-XSRF-TOKEN` (from the `XSRF-TOKEN` cookie) to mutating requests and treats any 401 as signed out.
- Dexie: `openDb(userId)` -> `rwx-<userId>` after `/me` resolves; `DbProvider`/`useDb()`; the skeleton global `rwx` database is removed (its `meta` store holds nothing worth keeping). Logout calls `POST /auth/logout`, closes the handle, clears the query cache, shows login. The local data of a user stays on the device until deleted (it is a cache only; the deferred offline phase decides on wiping it).
- i18n for the new strings: a minimal catalogue (en/ru/uk) chosen by device locale, structured so the Polish phase can extend it.
- Login page is a single GitHub button (visual from `docs/design/`, no dedicated design exists; ui-designer may only pick tokens). Home page is explicitly temporary.

## 7. Trade-offs
- Opaque DB-backed sessions over JWT: revocable, no refresh logic, one DB hit per request (fine at this scale).
- Open sign-up (no allow-list, no invitations); account deletion and export are in scope because of it.
- No dev bypass means local dev needs a GitHub OAuth App (two minutes of setup, documented). Rejected: mock mode, dev login (risk of polluted or exposed data).

## 8. Code layout (module `identity`)
- Root (published): `CurrentUser`, `CurrentUserProvider`, `NotAuthenticatedException`, `UserTimezoneChangedEvent`, `AccountExportContributor`.
- `internal`: `AccountService`, `ExternalProfile`, `IdentityConfig`.
- `internal.persistence`: `UserEntity`, `CredentialEntity`, `UserSettingsEntity` and their repositories.
- `internal.exception`: every other identity exception (`InvalidSettingsException`, `InvalidOAuthStateException`, `AccountDisabledException`); no Spring Security exception subclasses exist.
- `internal.web`: `MeController`, `SettingsController`, `ProblemAdvice`, `IdentityMapper`.
- `internal.github`: only what is GitHub-specific: `GithubOAuth2UserService`, `LoginSuccessHandler`.
- `security`: provider-agnostic `SecurityConfig`, `ProblemSecurityHandlers`, `UserPrincipal`, `SecurityContextCurrentUserProvider`, `ShortLivedAuthorizationRequestRepository`.
