# Design: datasource (Phase 2)

> Phase 2 re-plan (owner decision): the former combined `media-search` change was split. This folder is the provider/data-source machinery (module `datasource`, `/data-sources`, keys, defaults, SPI, resolvers, rate limit, error mapping, packages) and the Settings > Sources section. The product side of search, the add flow in `media` and the offline consequences are in `docs/openspec/changes/media-search/` (Phase 3); where the text below still speaks of the add sheet, search UI or create, read it as the Phase 3 consumer. Section numbers are unchanged; 8, the create flow of 12 and 13 moved.

Sources of truth: `api/openapi.yaml` and `backend/src/main/resources/db/migration/V001__initial_schema.sql`. Operation ids and field names below are the contract's.

**Revision 3 (owner add flow) supersedes revision 2: data sources are pluggable per type behind a small SPI, search returns entries with a server-generated canonical `sourceUrl` plus a trailing draft entry, and create takes `{id, sourceUrl}` only. Sections 4, 6, 7, 8, 12 and 13 are rewritten; 15 is the SPI, canonicalization and security design.**

**Revision 3.1 (owner answers): source ids are closed enumerations per resource (`BookSourceId` = `draft`, `open_library`; `MovieSourceId` = `draft`, `tmdb`; search lists use `BookSearchSourceId`/`MovieSearchSourceId`; the Open Library id is `open_library`, with an underscore, everywhere: contract, DB CHECK, config, registry); book search hits carry an optional `isbn` again (7, 12); the draft entry is hidden by the client when the library already has that title (8); there is no UI to paste a raw link, the API still accepts provider URLs (8).**

**Revision 4 (owner decisions, section 16 is authoritative where it differs): the module `search` is renamed `datasource`; users can choose a default source per resource type and save an API key per source (V001 `user_default_sources` and `user_source_keys`, 16.2, `changes/datasource-defaults`; `GET /data-sources` replaces `/search/sources` and `/external-data-sources`); error codes are source-agnostic (`source_key_*`, `Problem.source`); internal packages `book`/`movie`/`provider`; the text rules shared with `media` move to `common`; library audit. Text below keeps the module and key wording of earlier revisions only where section 16 does not change it; section names and operation ids in 2, 3, 5-8 are updated.**

## 1. Modules
- `com.javanix.rwx.datasource` (renamed from `search`, revision 4; package layout in 16.4): depends on `identity` (`CurrentUserProvider`, and `settings.SettingsService` (`get(userId).locale()`) to read the user's locale, see section 12), `common` (`StrictUrl`; since revision 4 also `Text` and `DraftLink`, so `datasource` builds the draft entry's Google link without depending on `media`, see 16.5) and the generated `api`. Internal: the source SPI and registries (section 15), `OpenLibrarySource`, `TmdbSource` with their HTTP client, `UserDataSourceService` (defaults and keys, 16.2), `RateLimiter`, `CatalogNormalizer`, controllers implementing the generated `data-sources` and `search` APIs. `/settings` GET/PATCH (timezone, locale, push) are not part of this change.
- Published API of `datasource` (the only types other modules may use): `MediaResolver<R, I>` (injected parameterized; no per-type sub-interfaces, see `datasource-simplification` round 2), the `BookRef`/`MovieRef` and item records they use, and the `CatalogException` family (section 12). The SPI itself (`BookSource`, `MovieSource`) is internal to `datasource`: adding a provider is a change inside this module, not an extension point for other modules.
- Direction: `media` depends on `datasource` (`allowedDependencies` of `media` lists `datasource`); `datasource` never depends on `media` (Modulith verification enforces it, no cycle). Search results still do not know the library: "in library" marks stay client-side (link equality or ISBN equality for provider entries; the draft entry is hidden when its normalized text equals a library title).

## 2. API key storage (no encryption for now) and user rows
- Owner decision: no encryption, no `user_secrets`, no `crypto` module. A user's key for a source lives in V001 `user_source_keys.api_key` (one row per user and source; no key version column until encryption exists; the `datasource` spec and `ROADMAP.md` still say "encrypted" in places: reconcile when encryption is revisited). Consequence to accept: DB dumps and backups contain keys in clear; protect them accordingly. The user's default choice is a different table, `user_default_sources`: every user has exactly one row per type from sign-up (16.2).
- Saving again replaces the key (upsert on the primary key `(user_id, source)`). All queries are scoped by `user_id`; another user's row is never reachable.
- Never returned: `DataSource` has no key field and no endpoint returns the key or a derived part (no last4); never logged; request/response body logging for `/data-sources` disabled; key excluded from exception messages; entity `toString` omits it. The request field `apiKey` is write-only in the UI (masked placeholder when saved, no reveal).
- No key status (owner decision): `DataSource` carries `tokenSaved` only. A 401 from the provider during search/details is `source_key_invalid` on that call and does NOT delete the key; nothing is remembered between calls, so the UI learns it from the failed search.
- `DELETE /data-sources/{resourceType}/{source}/key` removes the key immediately (16.2 for the row rules), 200 also when none.


## 3. TMDb key handling (the TMDb source's own rules)
- Accepted: TMDb v4 "API Read Access Token" (JWT, sent as `Authorization: Bearer`) or v3 API key (32 hex chars). The UI asks for the v4 read token (recommended; stays out of URLs and proxy logs) but v3 keys are accepted and sent as the `api_key` query parameter with the outbound URL never logged. Format check: 20..512 chars, `[A-Za-z0-9._-]`.
- Save = validate first (`TmdbSource.validateKey`, called by `UserDataSourceService`): `GET https://api.themoviedb.org/3/authentication`. 200 -> store, respond 200 with the refreshed lists. 401 -> 422 `source_key_rejected` (`Problem.source` = `tmdb`), nothing stored. Network/timeout/5xx -> 502/504, nothing stored (user may retry). Format violation -> 400 `validation` (the format rule belongs to the source).

## 4. Provider access
- Fixed hosts only: `openlibrary.org`, `api.themoviedb.org` (base URLs are properties for WireMock in tests; `https` enforced outside tests). The URL a client sends is only parsed (section 15.3), never requested: the outbound URL is always our configured base URL plus a provider id that matched a strict pattern: Open Library `^OL[0-9]{1,12}W$`, TMDb `^[1-9][0-9]{0,9}$`, TMDb type `movie|tv`. Query: trimmed, 3..200 chars. No redirects followed. Response body capped at 2 MB.
- Client: Spring `RestClient` on the JDK HttpClient; connect 3 s, read 8 s per request; no automatic retries. Header `User-Agent: RWX/<version> (<RWX_DATASOURCE_CONTACT>)` for Open Library (property required in every profiles).
- Open Library: `search.json` with the fields and audiobook filter from the search spec; details `/works/<id>.json`. Cover = `https://covers.openlibrary.org/b/id/<cover_i>-L.jpg` built server-side. Ratings are 0..5, matching the books schema.
- TMDb: every call passes `language` = the user's `user_settings.locale` (never null, fixed at sign-up), so titles and descriptions follow the UI language. `search/multi`, drop `person`, first 10; details: movie `/movie/{id}`, tv `/tv/{id}` (no credits: no stored field uses them; books fetch the work and a key lookup in parallel on virtual threads, section 12). TV status mapping `Ended|Canceled` -> `ended`, other non-null -> `ongoing`, null -> absent. Image base from `/configuration`, cached in memory 24 h (global, not user data); poster size = smallest `poster_sizes` entry with width >= 250 (typically `w342`), fallback `w342`.
- Every search hit carries a canonical `sourceUrl` built server-side by the same function the source uses to canonicalize incoming URLs (section 15.3); details carry the same string as `externalLink`. The client never builds a provider URL.
- Short in-memory cache (Caffeine, 10 min, max 1000 entries) of normalized provider results (search hits without the draft entry, and resolved items) keyed by (source, query or canonical ref, locale for TMDb), for Open Library and for TMDb after the user's key check; holds public catalogue data only. Behind `rwx.datasource.cache.enabled` (default true). Revision 4 (16.6): implemented with Caffeine's `Cache.get(key, loader)` directly (atomic, concurrent identical misses load once).

## 5. Rate limiting
Per-user in-memory limits (single replica assumed; move to Postgres/Redis if the Helm chart ever runs >1 replica, see 16.6): search 30/min (burst 10), details 60/min (burst 20), key save 5/min. Exceeded -> `429` problem `rate_limited` with `Retry-After`. Global outbound guard: at most 8 concurrent provider calls. Revision 4: Spring `@ConcurrencyLimit(policy = REJECT)` on `OutboundGate.run` (limit from `rwx.datasource.http.max-concurrent`, default 8) replaces the semaphore, so an excess call fails at once (no 2 s wait) with 503 `provider_error` (section 6; this also settles the earlier 502-or-503 disagreement between sections 5 and 6). TV refresh is client-driven (sequential detail calls), so it fits the details bucket; the client must back off on 429.

## 6. Error mapping (RFC 9457 problems with `code`)
Source-agnostic since revision 4: a problem about one data source names it in the `source` member of `Problem` (`open_library` or `tmdb`), never in the code.
| Cause | Status | code | `source` |
|---|---|---|---|
| query < 3 or > 200 chars or with control characters, `source` not in the enum or `draft` or not in this type's list, bad `sourceUrl` length, bad key format | 400 | `validation` | no |
| `sourceUrl` not recognized by any source of the resource (also a draft link on the details endpoints), or invalid content | 422 | `unsupported_source` | no |
| a source that needs a key was used without a saved key | 409 | `source_key_missing` | yes |
| the provider answered 401 to the saved key on a search/details/create call | 409 | `source_key_invalid` | yes |
| save: the provider rejected the submitted key | 422 | `source_key_rejected` | yes |
| `/data-sources/{type}/{source}/...` for a pair that is not registered, or a key operation on a source without a key | 404 | `not_found` | no |
| provider 404 on details | 404 | `not_found` | no |
| provider 404 on create from a reference | 422 | `source_not_found` | yes |
| provider 429 | 503 + `Retry-After` | `provider_rate_limited` | yes |
| provider 4xx other / 5xx / malformed JSON / empty body on a 2xx | 502 | `provider_error` | yes |
| any other `RestClientException` out of a provider call (e.g. an I/O error while the body is read), fixed text without URI or message | 502 | `provider_error` | no |
| our outbound concurrency guard is full | 503 | `provider_error` | no |
| timeout / connect failure | 504 | `provider_timeout` | yes |
| our per-user limit | 429 | `rate_limited` | no |
The same codes apply to `POST /books` and `POST /movies` when a provider URL is resolved (section 12), with one difference: provider 404 on a create is `422 source_not_found` (a 404 on a collection POST would read as "endpoint missing"), while the details endpoints keep `404 not_found`. `unsupported_source` is decided before any outbound call and before the rate limiter. A resolved record that fails the stored-item assertion (title blank, ...) is `502 provider_error`.

Problem `detail` never echoes provider bodies, URLs, queries or the key. Logs: provider, status, latency at INFO; query text only at DEBUG.

## 7. API (`/data-sources*` is in `api/openapi.yaml`; the rest is Phase 3)
Phase split: `/data-sources*` is the only part in the contract and implemented in Phase 2; everything below about `/search/*` and `POST /books`/`/movies` describes Phase 3 and is NOT in `api/openapi.yaml` now (they return with `media-search`). `/search/books`, `/search/movies` and their `/details` endpoints and `POST /books`/`POST /movies` are in the contract but are implemented in Phase 3 (`media-search`); in Phase 2 there is no controller behind them.
- `GET /data-sources` (`listDataSources`, revision 4; replaces `GET /search/sources`) returns `DataSources`: `books` and `movies`, each an ordered list of `DataSource` (`id`, `label`, `requiresKey`, `isDefault`, `isEffective`, `available`, `tokenSaved`). The order is server configuration (`rwx.datasource.books.sources`, `rwx.datasource.movies.sources`; today `open_library` and `tmdb`). `isDefault` is the user's stored choice, or the first of the list when none; `isEffective` is the source a search without `source` uses (16.2). Open Library is always available; TMDb is available once the user has a saved key. The search and details endpoints keep their `/search/...` paths and operation ids (16.1).
- `GET /search/books?q=&source=` (`searchBooks`) and `GET /search/movies?q=&source=` (`searchMovies`): `q` trimmed 3..200 characters; `source` optional (omitted = the user's effective source of that type; an id not in the list is 400). The server calls the source upstream and returns a bare array of at most 10 provider hits in the source's order, each `BookSearchHit`/`MovieSearchHit` with `kind: provider`, a canonical `sourceUrl`, and the display fields (title, author/original title, year, rating, cover/poster, movie `type`); then ALWAYS one last entry with `kind: draft`, `title` = the trimmed text and `sourceUrl` = `DraftLink.build(text)` (Google search link; the server does not know the library, so it always returns this entry and the client hides it by rule, section 8). No provider id is exposed. A book hit carries an optional `isbn` (revision 3.1): the first non-blank ISBN the provider returns for the work, trimmed and not otherwise changed or validated (owner decision, DS-B15 cancelled), absent when there is none, by the same function (`OpenLibrarySource.pickIsbn`: first non-blank in the provider's order) that `resolve` applies, so the hit and the stored item agree in the normal case. Why: revision 3 dropped it from the hits as a simplification (hits no longer carried provider ids), not for a technical reason; the client needs it to mark the same book under another work id with its existing `normalizeIsbn` rule, besides `sourceUrl` equality. The server's ISBN rule stays authoritative (409 with `existingId` after resolve). Residual gap: the hit's and the resolved work's first ISBN can differ when Open Library orders editions differently in two calls; then the client misses the mark and the 409 catches it. A provider failure is an error response (the client builds the draft entry itself).
- `GET /search/books/details?sourceUrl=` (`getBookDetails`) and `GET /search/movies/details?sourceUrl=` (`getMovieDetails`) return exactly what create stores for that URL (`BookDetails`/`MovieDetails`, `externalLink` = the canonical URL). Decision: the preview is by `sourceUrl`, not by provider id. Reasons: it is the same input as create, so the preview and the stored item cannot drift and share one recognizer, resolver and cache; it works for a pasted provider URL; the contract exposes no provider ids or movie/tv path segments (which would be source-specific and ambiguous across sources, e.g. the same number in two providers); the TV refresh can pass the stored `externalLink`. Cost: a URL in a query string (public catalogue URLs only, capped at 4096, never logged above DEBUG). A draft link is 422 `unsupported_source` (a draft has no details).
- Defaults and keys (revision 4): `setDefaultDataSource` (`PUT /data-sources/{resourceType}/{source}/default`), `saveDataSourceKey` (`PUT .../key`, body `{apiKey}`), `deleteDataSourceKey` (`DELETE .../key`); all three return the refreshed `DataSources` (a change of one source moves flags of others). They replace `listExternalDataSources`, `configureExternalDataSource` and `removeExternalDataSource`. Semantics: 16.2.
- Create: `POST /books` `{id, sourceUrl}` and `POST /movies` `{id, sourceUrl}` (section 12); search, details and create share the recognizer, the resolver and the cache.
- The old `/search/books/{sourceId}`, `/search/movies/{type}/{sourceId}`, `BookSearchHit.sourceId`/`isbn` and the reference create shape are removed from the contract; there are no external clients.
- Error responses are `application/problem+json` using `Problem.code` from section 6.

## 8. Frontend design (Phase 2 part)
- The add sheet, search rules, in-library marks, add-from-entry, preview, TV refresh, link rendering and image CSP moved to Phase 3: `docs/openspec/changes/media-search/design.md` section 8.
- Settings "Sources" (frontend DS-F4, fills the empty `SourcesSlot` of the `settings-screen` screen, which is the only screen after sign-in in Phase 2): one `useDataSources()` query on `GET /data-sources` shared with the add sheet; the three mutations (`setDefaultDataSource`, `saveDataSourceKey`, `deleteDataSourceKey`) replace the query data with the returned lists, so a future add sheet reflects a change at once. Two groups (Books, Movies and TV), one row per source with its label and state (available / key saved / needs a key). A default choice control (radio among the sources of the group) is shown only for a group with two or more registered sources, so it is invisible while each type has one; it allows an unavailable source (the row then says which source is used instead until a key is saved). For a source with `requiresKey`: the write-only key field with a masked placeholder when saved (no reveal), Save / Delete, a "how to get a key" link (TMDb: v4 read access token), error text per `code` (`source_key_rejected` = wrong key, naming the source from `Problem.source`).

## 9. Trade-offs
- Server resolves a `sourceUrl` (owner decisions) instead of the client composing the item: the client cannot submit forged or stale metadata, the outbox payload is one string and stays valid for as long as the id exists, and validation of provider fields moves to the ingest side. Cost: `media` depends on `datasource`, a create takes a provider round trip (seconds, can fail), and the create endpoint has provider error modes (section 12). Rejected: client-composed items (previous design); a separate `POST /library/add-from-source` endpoint (a second create path); provider ids in the client contract (revision 2: source-specific, collide across sources, and the movie `type` had to be sent next to the id).
- URL-keyed contract vs id-keyed: a URL is a longer input and needs strict canonicalization on the server (section 15.3); in return one flat shape serves every present and future source, paste-a-link is free, and the client needs no provider knowledge.
- Source SPI inside `datasource` only, config-ordered registry: adding a provider is one class plus one config entry, no plugin loading; not published to other modules so `media` never learns provider specifics.
- In-memory rate limiting: simplest, no new infra; resets on restart and is per replica.
- Plaintext key at rest: simplest, accepted by the owner for now; v4 vs v3 token: accept both, v3 in a query string is a leak risk mitigated by never logging outbound URLs.
- No key status: a refused saved key is reported by the failing call (`source_key_invalid`), not stored or remembered.
- All-or-nothing resolve (every provider call needed for a field must succeed): a transient Open Library or TMDb blip fails the add, which is safe to retry, instead of storing a permanently thin record (there is no refresh or promote in v1). The previous best-effort description for books is dropped for that reason.

## 12. Published catalog API (Phase 2 part; the create flow in `media` and the offline consequences moved to `media-search` design, sections 12 and 13)

### Published catalog API (`search`)
- `MediaResolver<BookRef, BookItem>`: `Optional<BookRef> identify(String sourceUrl)` (pure: no I/O, no user, no key; the recognition and canonicalization of section 15.3 over the registered book sources in list order) and `BookItem resolve(UUID userId, BookRef ref)`. `MediaResolver<MovieRef, MovieItem>` likewise with `MovieRef` (adds the movie/tv `type`). `BookRef(source, externalId)` and `MovieRef(source, type, externalId)` (both `MediaRef`) are what `media` uses for the identity pre-check and then hands back to `resolve`. Records are `datasource`-owned (not generated API models): `BookItem(ref, externalLink, title, author, description, coverUrl, year, rating, isbn)` and `MovieItem(ref, externalLink, title, originalTitle, description, posterUrl, year, rating, tvStatus, seasonCount)`; `externalLink` is the source's `canonicalUrl(ref)`. `BookCatalogService` and `MovieCatalogService` implement `MediaResolver<R, I>` (`identify`, `resolve`) through the generic `CatalogService`. All values are normalized (below). The user id is a parameter, not read from the security context, so the same call works from the REST path, `/sync/push` and tests; the key and the locale are looked up inside `search` by that id.
- `identify` does not check availability: a TMDb URL is recognized without a key, so the duplicate pre-check and a re-POST work, and the missing key surfaces from `resolve` as `source_key_missing`.
- The details controllers call `identify` + `resolve` with the current user (a draft URL or an unrecognized one: 422 `unsupported_source`) and map the item to `BookDetails`/`MovieDetails`: preview and create cannot drift, share the Caffeine cache, and the limiter charges one details token per call.
- Failures are unchecked `CatalogException` subclasses published with the API: `SourceNotFound`, `SourceKeyMissing`, `SourceKeyInvalid`, `ProviderTimeout`, `ProviderError`, `ProviderRateLimited(retryAfter)`, `RateLimited(retryAfter)`; each carries `source()` (the wire id, null for `RateLimited`) so the advice can fill `Problem.source` (16.3). One `@RestControllerAdvice` in `datasource` maps them (section 6); `media` does not catch or translate them, except that the details controllers turn `SourceNotFound` into 404 `not_found`. `UnsupportedSourceException` lives in `common`.
- Resolution rules. Open Library: `GET /works/<id>.json` is the existence and title/description source (404 -> `SourceNotFound`); `GET /search.json?q=key:/works/<id>&fields=...&limit=1` supplies author, first publish year, `cover_i`, first non-blank ISBN, `ratings_average`; the two run in parallel on virtual threads; an empty search result leaves those fields absent, a failed call fails the resolve. TMDb: `GET /movie/<id>` or `/tv/<id>` with the user's locale gives everything (no credits). Overall deadline for one resolve: 10 s (then `ProviderTimeout`).
- Ingest rules (each source builds its items itself; revision 5 dissolved `CatalogNormalizer`, the shared `Texts` has only title/optional/cut and `body` (an empty 2xx body, which the declarative client returns as null, is a `ProviderError`), the rest lives in `OpenLibrarySource` and `TmdbSource`): title trimmed, empty -> `ProviderError`, cut at 500; author cut at 500; description blank -> null, cut at 20000; year kept only in 1..3000; rating clamped to 0..5 (books) or 0..10 rounded to one decimal, invalid -> 0; cover/poster always built by us on `https://covers.openlibrary.org` or the TMDb image base, never copied; ISBN not validated or normalized (owner decision, DS-B15 cancelled: the value comes from a service we trust); `pickIsbn(list)` = the first non-blank one in the provider's order, trimmed, used for both search hits and resolve; the link is `ref.canonicalUrl()`; TMDb status mapping (section 4).

## 15. Sources: SPI, registry and canonicalization (revision 3)

### 15.1 SPI (internal to `search`)
```
interface BookSource {
  BookSourceId id();                             // generated enum (OPEN_LIBRARY = "open_library"), stored as books.source, never DRAFT
  String label();                                // "Open Library"
  boolean isAvailable(UUID userId);              // false while a required key is missing
  Optional<BookRef> recognize(URI url);    // pure: this source's URL patterns -> canonical ref, or empty
  List<BookHit> search(UUID userId, String q);   // upstream keyword search, parsed, <= 10; each hit carries its sourceUrl (the source's canonicalUrl(ref))
  BookItem resolve(UUID userId, BookRef ref);    // details from OUR configured base URL
}
```
`MovieSource` is the same with `MovieRef`/`MovieHit`/`MovieItem` (the `type` is part of the ref). Revision 4 (16.4): both extend `SourceInfo` (`id()`, `resourceType()`, `label()`, `requiresKey()`, `validateKey(String)`), and `isAvailable` reads the user's saved key from `UserDataSourceService`. `recognize` does no network and no user lookup, so it is safe to run on any input before any budget is spent.

### 15.2 Registry
`BookSources` and `MovieSources` are the ordered lists: the `SourceInfo` beans in `@Order` order, grouped by resource type (there are no `rwx.datasource.*.sources` properties; every source bean is registered). The default per type is `rwx.datasource.books.default` / `.movies.default` (`open_library` / `tmdb`; it must be a registered source of that type, else startup fails). They back `/search/sources` (per-user availability), `source` parameter validation, and `identify` (first source whose `recognize` is present wins; sources own disjoint hosts, a test asserts no URL is recognized by two). Draft is not a registered source (it is built into `media` and `common`); a draft is never a `SourceInfo` bean; a new source starts with a new value of the contract enum and a CHECK extension, then a bean. The `source` query parameter is the same enum, so an unknown value is rejected by the generated validation (400) and `draft` or a source of the other type by the registry (400).

### 15.3 Canonicalization per source (`recognize`)
Common first step (`datasource.SourceUrl`, formerly `StrictUrl`; see change `datasource-simplification`): the input is at most 4096 characters and parses with `java.net.URI` (parse failure -> not recognized); scheme `http` or `https` and a non-empty host are required, scheme and host are lowercased, and userinfo, port and trailing dot are exposed, not rejected. Each source's `recognize` rejects userinfo, a port other than the scheme default and any host outside its exact host set (a trailing dot never matches); the draft source accepts `https` only and applies its own printable-ASCII, userinfo and port checks in `DraftLink`. Canonical output is always `https`. The path is compared raw, before percent-decoding. Query and fragment are dropped unread. A source matches on the exact host set and a path regex; the id group must match its strict pattern, otherwise the URL is not recognized.

| Source | Hosts | Path pattern (raw path) | Ref | Canonical URL |
|---|---|---|---|---|
| `open_library` (books) | `openlibrary.org`, `www.openlibrary.org` | `^/works/(OL[0-9]{1,12}W)(/.*)?$` (slug and any trailing path accepted and discarded) | id = group 1 | `https://openlibrary.org/works/<id>` |
| `tmdb` (movies) | `www.themoviedb.org`, `themoviedb.org` | `^/(movie\|tv)/([1-9][0-9]{0,9})(-[^/]*)?(/.*)?$` (slug and trailing path such as `/season/1` discarded; `?language=` dropped) | type = group 1, id = group 2 | `https://www.themoviedb.org/<type>/<id>` |
| draft (built into `media`/`common`) | `www.google.com` | exactly `/search` with one `q` | text | `https://www.google.com/search?q=<encoded text>` |

Not recognized on purpose: Open Library edition (`/books/OL..M`), author and search pages, TMDb person/collection pages, short links, other hosts; they are 422 `unsupported_source` (edition-to-work resolution could be added later as a recognizer-side feature). Examples: `https://openlibrary.org/works/OL45804W/Fantastic_Mr._Fox?edition=ia%3Afoo` -> `https://openlibrary.org/works/OL45804W`; `http://www.themoviedb.org/tv/1396-breaking-bad/season/1?language=ru-RU#x` -> `https://www.themoviedb.org/tv/1396`; `https://themoviedb.org/movie/603abc` and `.../movie/0603` -> not recognized; `https://openlibrary.org.evil.com/works/OL1W`, `https://openlibrary.org@evil.com/works/OL1W`, `https://openlibrary.org:8443/works/OL1W` -> not recognized. Property: `recognize(canonicalUrl)` returns the same ref (idempotent), and every search hit's `sourceUrl` is `canonicalUrl` of its ref (so the client's string equality with a stored `externalLink` is exact).

### 15.4 Security checklist (search side)
- SSRF: the client URL is parsed and discarded; the outbound request is `configured base URL + path built from the validated id`; no redirects followed; host and scheme fixed by configuration (WireMock base URLs in tests only); `recognize` runs before any outbound call and before the rate limiter; the details/preview endpoints go through the same path, so a `sourceUrl` can never make the server request an arbitrary host.
- Length and charset: `sourceUrl` 4096 and `q` 200 are bounded at the edge; `q` is also checked with the draft text rules (no control or bidi characters) because it becomes the draft entry.
- Output: hits and details carry only server-built URLs (`sourceUrl`/`externalLink` canonical, covers on fixed hosts, https only); the client renders a link only if it parses as https; titles and descriptions are text only (React escapes; no HTML from providers is ever interpreted: descriptions are plain text, tags are not rendered).
- Logs: provider, status, latency at INFO; `q`, `sourceUrl` and draft text at DEBUG only; problem `detail` never echoes the URL, the query or provider text.
- Isolation: availability, keys, locale and rate limits are per user; identity lookups are scoped by `user_id`.

Note: the stored-item assertion in media requires `externalLink` to equal the canonical URL the source derived (the source's `canonicalUrl(ref)`), so a provider URL with a slug can never be stored as typed.

### 16.2 User data sources (two tables: `user_default_sources`, `user_source_keys`)
Owner-approved redesign (V001 edited in place, nothing is deployed). It replaces the single `user_data_sources` table with its default flag, partial unique index, "not empty" CHECK, row lock, retries and in-memory status: a default and a key are different facts and now live in different tables, so every invariant is a primary key.

**V001 changes, exact:**
1. Delete the section "external_data_source_configuration: API keys for third-party services" (header comment, table, its four `COMMENT ON` lines).
2. In the same place (after `user_settings`, before `applied_mutations`) add:
```sql
CREATE TABLE user_default_sources (
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  resource_type text NOT NULL,
  source text NOT NULL,
  PRIMARY KEY (user_id, resource_type),
  CONSTRAINT valid_user_default_source CHECK (
    (resource_type = 'book' AND source IN ('open_library')) OR
    (resource_type = 'movie' AND source IN ('tmdb')))
);

CREATE TABLE user_source_keys (
  user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  source text NOT NULL CHECK (source IN ('tmdb')),
  api_key text NOT NULL CHECK (char_length(api_key) BETWEEN 1 AND 512),
  PRIMARY KEY (user_id, source)
);
```
plus `COMMENT ON` for both tables and for `user_default_sources.resource_type` / `.source` and `user_source_keys.source` (see V001). The primary key of `user_default_sources` is what guarantees one default per user and type; the pair CHECK is the old one (extending the list is an ALTER). `user_source_keys` lists only sources that need a key. No `api_key_version`, no timestamps, no surrogate id (nothing reads them; a key version arrives with encryption, as a new migration after the first deploy). The primary keys lead with `user_id`, so there is no extra index. `AccountDataTests` seeds both tables for each user so the zero-rows assertion is not vacuous.

**Entities and repositories:** two small entities with an embedded composite id (`UserDefaultSourceEntity.Id(userId, resourceType)`, `UserSourceKeyEntity.Id(userId, source)`, nested records) and two repositories with one derived query each (`findByIdUserId`) plus the inherited `findById`/`save`/`deleteById`. No `@Query`, no native SQL, no locks. `UserSourceKeyEntity.toString` omits the key.

**Derived state** for one user and one resource type, from the registry (ordered, `requiresKey` per source), the stored default of the type (one row or none) and the user's saved keys (ids of sources with a key):
- `tokenSaved(s)` = `requiresKey(s)` and a key row exists; `available(s)` = not `requiresKey(s)` or `tokenSaved(s)`.
- `isDefault(s)` = the stored default of the type; if there is none (a type registered after the user signed up) or its source is no longer registered, the configured default. Exactly one per list.
- `isEffective(s)` = the default if available; else the first available source in list order; else the default (then a search answers with that source's own `source_key_missing`). Exactly one per list. The fallback never writes anything: the stored choice survives, and saving the key again makes it effective again.
There is no key status: the contract carries `tokenSaved` only. A key the provider refuses on use is reported by that call (`source_key_invalid`, the key is kept), not remembered.
The default affects only a search without `source` and the add sheet preselection. It does not affect `identify`, `resolve`, create from a URL or details by URL: a pasted TMDb URL resolves with the saved TMDb key whatever the default is.

**Operations** (all scoped by the session user; there is no user or row id in any path):
- Sign-up: the `UserCreatedEvent` listener saves the configured default of every type in the sign-up transaction. There is no lazy repair of a missing row (the derivation falls back to the configured default).
- `setDefaultDataSource(type, source)`: pair must be registered, else 404 `not_found`. `save` of the row `(user, type)` (an update). Idempotent. Allowed for an unavailable source. The last of two parallel changes wins.
- `saveDataSourceKey(type, source, apiKey)`: pair registered and `requiresKey`, else 404. Per-user `KEY_SAVE` limit, the source's format check (400), the source's `validateKey` against the provider (422 `source_key_rejected`, 502, 504), then `save` of `(user, source)` (upsert by merge). Any failure stores nothing and keeps an older key.
- `deleteDataSourceKey(type, source)`: pair registered and `requiresKey`, else 404. `deleteById`; absent is a no-op. A default row is never touched: the choice is kept, the source becomes unavailable and `isEffective` moves on.
- Concurrency: nothing is locked. Different defaults change different rows, last wins. Parallel writes of one user's key for one source can make the database refuse the loser (two first saves both insert and hit the primary key; a save whose row a parallel delete removed updates nothing and Hibernate reports a stale state; two deletes of one row likewise). In each case the result equals the loser having run first, so the service catches `DataIntegrityViolationException` / `ConcurrencyFailureException` around that one write and ignores it, without retry. Found by `UserDataSourceServiceTests.parallelOperationsOfOneUserNeverFailAndLeaveAConsistentState`.
- Account deletion: cascade on both tables. Export: `dataSources` = the chosen defaults as `{resourceType, source}`; keys never.

**Stored defaults.** Owner decision: every user has exactly one stored default per type. `identity` publishes `UserCreatedEvent`, `datasource` inserts the rows in the sign-up transaction. The effective state is derived in code on each list (two queries, a handful of rows) and implemented once on the server, not repeated on the client (`isEffective`). Rejected: `default_*_source` columns in `user_settings` (identity-owned table, couples modules); a JSON blob (no constraints).

**Settings > Sources (F4)** uses this as in section 8: one query, three mutations that replace the cached lists, the default control only for a group with two or more registered sources (today none), the key form for `requiresKey` sources; a row says "Key saved" or "Needs an API key".

### 16.7 Risks
- `@ConcurrencyLimit` works through a Spring proxy: the guarded method must be called through the bean and be proxyable (public, or package-private in the same classloader); DS-B14 verifies it with a concurrency test.
- Caffeine's single-flight blocks waiters on the key's lock; an abandoned (interrupted) loader keeps the lock until its call ends (bounded by the per-request timeout), so a second caller for the same key waits at most that long inside its own deadline.
- The contract change breaks the build until DS-B10, and an unknown 409 code is read by the current frontend as `duplicate`: DS-B11 and DS-F8 ship together.
- `RWX_SEARCH_CONTACT` is renamed: a local `deploy/docker/.env` must be updated (the app fails fast with a clear message).
- Changing `Text.trim` changes the key of a title that starts or ends with U+001C-001F or U+FEFF (no deployed data, so no migration).

> Superseded (datasource-simplification, Round 7): `BookSources`/`MovieSources` no longer exist; `BookCatalogService`/`MovieCatalogService` hold the ordered source list (`sources()`, `source(id)`, `identify`) over `SourceDirectory`.

> Superseded (datasource-simplification, Round 9): `BookHit` and `MovieHit` are gone; `BookSource.search` returns `List<BookItem>` and `MovieSource.search` `List<MovieItem>` (partial items: `externalLink` is the canonical link, fields the search does not provide are null). `TmdbAuth` was merged into `TmdbSource`. `BookSource`/`MovieSource` are `MediaResolver`s themselves (raw, unthrottled `resolve`); `CatalogService` is the guarded composite. The `q` check uses the simplified draft text rules (no ISO control characters, no U+FFFD).

- The rules, where they live now: no absolute-URL escape (the interfaces take no `URI` argument, path ids and query values are URI variables, encoded as one segment; the base is the only origin); redirects off and connect/read timeouts (`HttpClient` with `Redirect.NEVER`, `JdkClientHttpRequestFactory.setReadTimeout`, which also stops a stalled body); response cap (Jackson `StreamReadConstraints.maxDocumentLength`, enforced while parsing, so no separate byte reader); status mapping and `Retry-After` clamp (`defaultStatusHandler` for every non-2xx, a 3xx included); fixed texts: a method-interceptor advice maps `RestClientException` to `ProviderTimeout` (I/O) or `ProviderError` (unreadable body) without the client message, which carries the URI; the log line `provider/status/latency` is a `ClientHttpRequestInterceptor`; the contact User-Agent and `Accept` are default headers; the outbound limit is `OutboundGate.run(MethodInvocation)` (still `@ConcurrencyLimit` through the Spring proxy) used as advice around every client method, so it also covers the body read; an empty 2xx body (null result) is a `ProviderError`.
- TMDb credential: every call takes `apiKey` and `authorization` (nullable, `required = false`); `TmdbSource.apiKey(key)` / `bearer(key)` pass the v3 key in the query or the v4 token in the header, the other is null (omitted). The language is a plain `language` argument from the stored locale. Cache, single-flight and "a failed load is not cached" are untouched (`cache.get(key, loader)` in the sources).
- Leniency: snake_case via the mapper's naming strategy, unknown properties ignored, nullable boxed components; `CoercionAction.AsNull` for string, integer, float and boolean input shapes (a number is never read as text, text never as a number) and a `DeserializationProblemHandler` that makes an object or array where a scalar or list is expected a null. The body is parsed whatever Content-Type the provider sends. A work description (string or `{type, value}`) stays a `JsonNode`.
- Known leniency gaps against `Json` (none occurs in the recorded fixtures or documented provider output): an integral value beyond `int` range in `first_publish_year`/`number_of_seasons`, and an array where a list of strings has a string item, fail the whole body (`ProviderError`) instead of being one absent value. Closing them means `Number`/`JsonNode` components, which is more code than the cases are worth.
- Size: main code of `provider` + `book` + `movie` 1868 -> 1855 lines (the replaced set `ProviderHttp` + `Json` + `OutboundGate` + both sources 822 -> 809). The gain is small: the win is less hand-rolled HTTP (URI building, byte reader, `Host`) and `JsonNode` walking, paid back by the two API files.
