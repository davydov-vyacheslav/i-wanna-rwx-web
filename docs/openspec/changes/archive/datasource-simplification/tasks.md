## Round 10
- [x] [Superseded: the table, entity, `UserDataSourceWriter`, row lock and `retryOnRace` described here were deleted by the storage redesign (`datasource` design 16.2, task DS-B18); the service now uses two tables with composite primary keys and plain `save`/`deleteById`.] `UserDataSourceRepository` / `UserDataSourceService`: no native SQL, no `ON CONFLICT`, no advisory lock. Every user has a default row per type from sign-up, so all writes of one (user, type) serialize on a row lock: `findByUserIdAndResourceTypeOrderBySource` (derived query with `@Lock`, `PESSIMISTIC_WRITE`, sorted by source so lock order is the same everywhere) is the first statement of every mutation, which then changes JPA entities (`markDefault`, `unmarkDefault`, `setKey`, `clearKey`). The writes live in the package-private `UserDataSourceWriter` (`@Transactional`: `createDefault`, `setDefault`, `putKey`, `removeKey`) because `saveKey` validates against the provider outside any transaction. A demotion is flushed before the promotion (the default index is not deferrable). Why: plain JPA instead of five native statements, a lock the database already owns, a much smaller service. A row lock covers only rows that exist when it is taken: a competitor that deleted a locked row or inserted a new one while we waited can still trip a unique index, so the service keeps a bounded retry (`retryOnRace`, 20 attempts with jitter, also on deadlock/serialization failures) in a new transaction. Tests: advisory-lock test replaced by a row-lock test, new parallel `saveKey`/`setDefault` test (one default, no exception); tests seed keys through `testkit.TestKeys`.
